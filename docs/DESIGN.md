# 밴드 합주 관리 앱 — 설계 배경 및 결정 기록

이 문서는 **왜 이렇게 설계했는지**를 기록한다.
도메인 모델·구현 범위·Phase별 완료 기준은 `docs/BUILD_PLAN.md`가 단일 출처이며,
이 문서에 중복해서 적지 않는다.

---

## 1. 서비스 개요

밴드원 개인이 각자 가입해서 사용하는 상용 서비스. 밴드 단위로 합주 일정을 기록·공유하고,
참석 여부를 확인하며, 비용을 N빵 정산하고, 합주 사진·영상을 게시판에 공유한다.

### 핵심 전제

이 앱은 합주실 예약을 대행하지 않는다. 실제 예약(전화·카카오톡·네이버예약 등)은
전적으로 앱 밖에서 이루어지며, 앱에서의 "일정 등록"은 **이미 외부에서 완료된 예약을
기록**하는 행위다. 합주실 사업자의 예약 시스템과 API 연동을 하지 않고,
실시간 가용시간 조회 기능도 없다. 합주실 정보 자체도 각 밴드가 직접 등록한다.

결제 역시 앱 밖에서 이루어지며, 앱 내부에서는 비용 분담 계산과 납부 체크까지만 담당한다.

## 2. 기술 선택과 근거

### 백엔드 — Java 21 / Spring Boot 3.x

개발자의 주력 스택이며, 단일 개발자가 유지보수할 서비스이므로 익숙함이 최우선 기준이었다.

### DB — PostgreSQL

기능적으로는 MySQL로도 무리 없는 요구사항이다. PostgreSQL을 택한 이유는 JSON 처리,
확장 기능, Testcontainers 조합의 성숙도 정도이며, **결정적인 이유는 없다.**
운영 편의나 익숙함을 이유로 MySQL로 바꿔도 설계에 영향을 주지 않는다.

> 초기에는 예약 시간대 겹침 방지를 위한 `tstzrange` + `EXCLUDE` 제약조건이
> PostgreSQL 선택의 주된 근거였으나, 도메인이 "기록 도구"로 정리되면서
> 겹침을 막지 않기로 했으므로 이 근거는 더 이상 유효하지 않다. (4.1 참조)

### 클라이언트 — Flutter

웹·iOS·Android를 모두 지원해야 하는데 개발자는 백엔드 중심이므로, 단일 코드베이스로
세 플랫폼을 커버하는 것이 현실적이다.

### 지도 — 네이버 지도

카카오맵과 비교했을 때, 네이버가 Flutter 공식 플러그인(`flutter_naver_map`)과
웹용 JS SDK를 모두 제공해 플랫폼 간 코드 일관성이 낫다. 카카오맵은 Flutter 공식 지원이
없어 커뮤니티 플러그인이나 웹뷰 우회가 필요하고, 이는 유지보수 리스크가 된다.

### 미디어 저장소 — Cloudflare R2

영상 서비스에서 비용을 좌우하는 건 스토리지 단가보다 **이그레스(다운로드) 비용**인데,
R2는 이그레스 요금이 없다. S3 호환 API라 AWS SDK for Java v2를 그대로 쓸 수 있다.

## 3. 인프라 구성 (월 1~5만원 예산)

- 서버: Oracle Cloud Always Free(ARM) 우선, 불가 시 저가 VPS(Contabo/Vultr 등)
- 단일 VM에 Docker Compose로 Spring Boot + PostgreSQL + Redis 운영
- Nginx 리버스 프록시 + Let's Encrypt HTTPS
- Cloudflare 무료 플랜 (DNS / CDN / DDoS 방어)
- Cloudflare R2 — 미디어 저장
- Firebase Cloud Messaging — 푸시 알림
- GitHub Actions — CI/CD (이미지 빌드 → GHCR → SSH 배포)
- UptimeRobot + Sentry 무료 티어 — 모니터링 / 에러 트래킹

단일 VM 구성이므로 **DB 백업이 유일한 데이터 보호 수단**이다. 배포 요건은
`docs/BACKLOG.md` 참조.

## 4. 주요 아키텍처 결정

### 4.1 시간대 겹침을 막지 않는다

이 앱은 실제로 일어난 일을 기록하는 도구다. 밴드가 같은 시간에 두 곳을 잡았거나
중간에 장소를 옮긴 경우도 있는 그대로 기록될 수 있어야 하므로, DB 제약조건이나
서비스 레이어 검증으로 등록을 차단하지 않는다.

대신 등록·수정 응답에 겹치는 일정 정보를 실어 보내고, 저장 여부는 사용자가 판단한다.

### 4.2 합주실(Room)은 밴드별로 독립 등록한다

여러 밴드가 같은 실제 장소를 각자 등록해도 별개 레코드로 둔다. 초기부터 마스터
테이블로 정규화하면 "같은 합주실인지" 판정하는 로직(주소 정규화, 중복 병합)이 필요한데,
서비스 초기에 그만한 가치가 없다.

**알려진 한계**: 이 구조 때문에 서로 다른 밴드가 같은 물리적 장소를 겹치게 등록해도
앱은 감지할 수 없다. 애초에 실제 예약 현황과 연동하지 않으므로 감지할 필요도 없다.

### 4.3 미디어는 클라이언트가 스토리지로 직접 업로드한다

대용량 영상을 백엔드 서버가 중계하면 소형 VM이 곧바로 병목이 된다. 백엔드는
presigned URL 발급과 업로드 완료 검증만 담당하고, 실제 파일 전송은 클라이언트와
R2 사이에서 직접 이루어진다.

비용을 실제로 좌우하는 건 보관 정책보다 **업로드되는 파일의 크기 자체**이므로,
클라이언트에서 업로드 전 압축(영상 720p·2~3Mbps, 이미지 리사이즈)을 강제한다.
서버 측 트랜스코딩은 CPU 부담이 커서 이 예산의 VM에는 맞지 않는다.

### 4.4 미디어 보관은 기간제 + 프리미엄 확장

무료 사용자에게 게시판 자체를 막으면 초기 사용자 확보에 불리하다. 무료는 기간제
보관으로 스토리지 증가를 예측 가능한 범위에 묶고, 보관 기간 연장을 프리미엄의
가치로 삼는다. 이것이 향후 유료 전환의 자연스러운 지점이 된다.

결제 도메인은 `PaymentGateway` 인터페이스에만 의존하도록 작성해, 실제 PG가 정해지면
어댑터만 추가하면 되도록 한다.

### 4.5 모듈형 모놀리스

단일 개발자가 운영하는 서비스에서 마이크로서비스는 순수한 비용이다. 도메인별 패키지로
경계를 나누고 서비스 레이어를 통해서만 참조하도록 해서, 나중에 분리가 필요해질 때
경계가 이미 서 있게 한다.

## 5. 추후 검토

- 실제 PG 연동 — 요금제 구조와 `PaymentGateway` 인터페이스까지는 구현 범위에 포함되며,
  실제 결제 어댑터는 요금 정책과 PG사 확정 후
- 개인정보처리방침 / 이용약관 정비 — 실사용자 대상 상용 서비스이므로 배포 전 필수
- Room 정규화 — 인기 합주실 통계·추천 기능이 필요해질 경우
- 정산 방식 확장 — 인원별 차등 부담(현재는 균등 / 참석자 기준 균등만)
