## 실행 규칙 — 한 항목씩 마무리한다 (2026-10-05 사용자 지시)

**같은 실수 방지:** POST-03에서 이모지60개만 시험하고 같은 화면에서 가능한 긴 한글·여러 줄·빈 입력을 남긴 채 다른 항목으로 넘어갔다. 또 정기 폼 연도 표시를 요금제 BILL-20과 잘못 연결했다. 현재 규칙은 이 분산 실행·잘못된 완료 연결을 막기 위한 것이며 문서 변경만으로 시험을 통과시키지 않는다.

1. 한 ID를 고르면 `시험`의 조건을 먼저 펼쳐 확인하고, **실행 가능한 조건을 모두 시험 → 조건별 결과·정리 기록 → 전체 판정 갱신 → 다음 ID** 순서로 진행한다. 특정 수정 조건만 확인하고 다른 실행 가능한 조건을 미루지 않는다.
2. 추가 기기·시간 대기·권한/준비물 부족 또는 선행 결함 때문에 실행할 수 없는 조건만 남겨 둘 수 있다. 무엇이 막혔는지·확인한 범위·재개 조건을 명시한다. 사용자 중지·연결 끊김은 마지막 진행 ID와 다음 조건을 남긴다.
3. 좁은 회귀는 **“이 조건만 완료”**, ID 전체는 **“모든 명시 조건 완료”**로 구분한다. 정기 폼/요금제, 앱내 알림/OS 푸시, 자동 테스트/실제 설치본처럼 다른 범위를 같은 증거로 완료 처리하지 않는다.
4. 결함은 이 문서의 **「현재 결함·+36 지정 회귀」 표**에 모으고 발견 번호·출시 번호·관련 ID·최신 실제 상태·상세 이력 위치를 연결한다. **클로드 등 수정 담당자는 이 표부터 읽는다.** 상세 실행은 QA_CHECKLIST, 출시 상태는 LAUNCH_REVIEW §1·영역표 양쪽에 기록한다. 수정된 설치본으로 재검증하기 전 실기기 완료로 바꾸지 않는다.
5. 캡처는 TEMP에 만들고 화면 확인 직후 PC·폰 임시 파일을 지운다. 화면 덤프·인증 임시 파일·일회용 계정/밴드도 정리 결과를 확인한다. 원본 갤러리·기존 계정/밴드 보존. 영구 유지 데이터는 별도 목적·정리 시점을 기록한다.
6. 기본 시험 계정은 사용자가 제공한 `demo.leader@bandule.com`(리더), `demo.guitar@bandule.com`·`demo.bass@bandule.com`·`demo.drum@bandule.com`(멤버)이다. 세 계정의 지정 테스트 밴드 역할을 사용하되 실제 화면/API로 역할을 확인한다. 사용자 본인 계정은 일반 시험·삭제 대상으로 사용하지 않는다. 비밀번호는 이 문서나 저장소에 적지 않는다. 가입/탈퇴 시험 등은 새 일회용 계정으로 한다.
7. **🤖 클로드 확인 완료 / 👤 사용자 확인 완료 표시가 있는 항목은 Codex 가 실기기로 다시 시험하지 않는다**(사용자 지시 2026-10-05). 시험 조건 **전체가 서버 동작이거나 운영 절차**라서, 실제 DB 로 도는 통합 테스트나 실제 운영 실행이 조건을 그대로 재현한 것만 이렇게 표시했다. 화면·입력·알림 표시 같은 앱 쪽 조건이 하나라도 남은 항목에는 붙이지 않았다(그 부분은 계속 Codex 담당). 현재 목록: OPS-02·OPS-11·REC-02·REC-07·CAL-05·CAL-08·SET-02·SET-06·BAND-10·REC-04·AUTH-07·AUTH-18·AUTH-20·REC-05·MEDIA-09·MEDIA-10·PUSH-05·PUSH-10·PUSH-17·PUSH-19·BILL-14·BILL-17·BILL-19·BILL-21·BILL-22·BILL-32·BILL-33·BILL-35·PRIV-01·PRIV-02·PRIV-03·PRIV-10·OPS-01·OPS-13·OPS-17·OPS-19·BILL-34·ROOM-02·REC-08·BILL-13·BAND-07·BILL-23·BILL-24(🤖, BILL-23 은 사용자 결정 포함, BILL-24 는 사용자 허용 로컬 격리 환경), OPS-16·AUTH-05·MEDIA-04(👤). 이 표시를 되돌리려면 근거 테스트가 틀렸다는 실제 증거를 함께 적는다. 관련 서버 코드가 바뀌면 클로드가 다시 확인한다.

### 다음 ID로 넘어가기 위한 필수 조건 — 2026-10-05 재지시

- **작업 단위는 QALIST QA ID 하나다.** QA-R 결함 번호·출시 U 번호를 별도 작업 단위로 삼아 관련 ID의 남은 조건을 건너뛰지 않는다. 현재 작업 ID를 QA_CHECKLIST 최신 절에 적고 동시에 하나만 활성화한다.
- **첫 UI/API 실행 전에 조건표를 만든다.** `시험`·`이번에 할 일`·연결 결함의 조건을 입력/상태/진입경로별로 한 행씩 펼친다. 각 행에는 기대 결과, 실제 결과/증거 위치, 판정, 정리 결과를 적는다. 이미 확인한 증거는 날짜·빌드·경로가 그 조건과 정확히 같을 때만 연결하며 자동 재시험하지 않는다.
- **전환 허용 조건:** 모든 행이 ① 실제 확인 완료(증거·정리 확인 포함), ② 실제 실행 후 기대 불일치(재현 증거·현재 결함 연결·정리 기록, 전체 ❌ 유지), 또는 ③ 규칙2의 허용 사유로 실행 불가(구체적인 막힘·확인 범위·재개 조건 포함)여야 한다. 결함이 있어도 그 ID의 다른 실행 가능한 조건은 끝낸다. `미실행`·`진행 중`·막연한 `준비 필요` 행이 하나라도 있으면 다른 ID 시작 금지다. 기다리는 동안 할 수 있는 일은 현재 ID의 준비·기록·정리뿐이다.
- **금지 사유:** 시간 절약, 같은 화면/코드, 회귀만 먼저, 다음 항목 준비, 다른 계정이 편함, 자동 테스트 통과, 좁은 회귀를 🟡로 기록함은 전환 사유가 아니다. 계정·기기·권한이 이미 있으면 준비하여 현재 조건을 실행한다.
- **종료 검사:** 조건표의 미실행/진행 중 0행 → 시험 데이터/설정 정리 확인 → QALIST 전체 ID 판정 → LAUNCH_REVIEW §1·영역표 갱신 → 다음 ID 순서다. 실행 불가 조건이 있으면 🟡/❌이며 조건별 재개 조건을 보고한다. 사용자 중지/연결 끊김 때는 현재 ID·다음 조건을 기록하고 멈춘다.
- **✅ 보고 제한:** 조건표 전 행이 확인 완료일 때만 “ID 모든 명시 조건 완료”라고 말한다. 결함 회귀 통과는 해당 ID 안의 증거로만 기록한다. 이 절을 적었다는 사실은 실제 시험의 완료 근거가 아니다.
