- 토큰 갱신의 확인·교체·재시도 응답 저장·무효 토큰 처리를 Redis Lua로 묶었다.

  인증번호가 유지되는 것도 확인했다. Flutter 두 화면에서도 같은 입력을 제출 전에 안내한다.

  맨 위의 2026-09-13 두 항목에 기록했다.

## 발견 1 — [P2] 동시에 갱신하면 정상 요청을 토큰 재사용으로 오인해 전 기기 세션을 지운다

**사용자에게 생기는 일**

같은 갱신 토큰을 보낸 두 요청이 겹치면, 정상적인 재시도인데도 로그인을 유지하지 못할 수 있다.
한 기기의 문제로 다른 기기의 갱신 세션도 함께 삭제된다. 기존 access 토큰은 만료 전까지
남으므로, 모든 화면이 즉시 로그아웃된다는 뜻은 아니다.

**원인과 위치**

- `src/main/java/com/yeka/bandapp/user/service/AuthService.java:132` — 세션 존재 확인.
- 같은 파일 `146`~`147` — 토큰 교체와 재시도 응답 저장을 따로 실행.
- 같은 파일 `135`~`143` — 세션도 재시도 응답도 없으면 전 기기 세션 삭제.
- `src/main/java/com/yeka/bandapp/common/security/RefreshTokenStore.java:52` — 교체 자체도
  이전 토큰 삭제·새 토큰 저장·만료 갱신이라는 별도 Redis 명령이다.

**재현한 순서**

1. 한 사용자에게 두 기기의 refresh 세션을 만든다.
2. 요청 A가 첫 기기의 토큰을 교체한 뒤, 재시도 응답을 저장하기 직전에 멈춘다.
3. 요청 B가 A와 동일한 옛 토큰으로 갱신한다.
4. B는 옛 세션도 재시도 응답도 찾지 못해 `REFRESH_TOKEN_INVALID`를 던지고 모든 세션을 지운다.
5. A는 성공 응답을 반환하지만 그 응답의 새 refresh 토큰도 이미 삭제된 상태다.

실제 `AuthService`, `RefreshTokenStore`, JWT 발급 코드를 실행했다. Redis 명령은 메모리 저장소로
대체하고, 요청이 겹치는 순서를 강제로 만들었다. 운영 부하 시험이나 실제 동시 HTTP 요청 측정은 아니다.

관찰값:

```text
overlapping retry error=REFRESH_TOKEN_INVALID
first successful response has active refresh=false
other device still active=false
```

**수정 방향**

Redis에서 세션 확인·토큰 교체·재시도 결과 저장을 하나의 원자적 처리로 묶는다.
동시에 같은 토큰을 보내도 같은 결과를 받고 다른 기기의 세션이 남는지 회귀 검증한다.
기존 `RefreshTokenGraceIntegrationTest`는 순차 재시도만 검증하므로 이 경우를 잡지 못한다.

## 발견 2 — [P2] 허용된 한글 비밀번호가 가입·재설정 중 서버 오류를 일으킨다

**사용자에게 생기는 일**

예를 들어 `가`를 25번 입력한 비밀번호는 25자여서 안내된 8~64자 조건을 만족한다.
하지만 암호화 단계에서 예외가 발생해 가입·비밀번호 재설정이 실패한다.

**원인과 위치**

- `src/main/java/com/yeka/bandapp/user/dto/SignupRequest.java:13`
- `src/main/java/com/yeka/bandapp/user/dto/PasswordResetConfirmRequest.java:17`

두 입력은 문자 수만 확인한다. 현재 사용하는 BCrypt 구현은 72바이트를 초과하면 거부한다.
위 예시는 UTF-8로 75바이트다. 가입의 `AuthService.java:73`, 재설정의
`PasswordResetService.java:81`에서 발생하는 `IllegalArgumentException`은
`GlobalExceptionHandler.java:66`의 일반 오류 처리로 들어가 HTTP 500이 된다.

**재현 결과**

프로젝트에 설치된 실제 Bean Validation과 `SecurityConfig`의 비밀번호 인코더를 실행했다.

```text
signup validation errors=0
reset validation errors=0
password encoder rejected validated input: password cannot be more than 72 bytes
```

검증 통과와 인코더 예외는 실행으로 확인했다. HTTP 500 변환은 예외 처리 코드에서 확인했다.

**수정 방향**

현재 BCrypt를 유지하면서 가입·재설정에 UTF-8 72바이트 제한을 검증하고,
사용자가 이해할 수 있는 입력 오류를 반환한다. 클라이언트 안내도 함께 맞춘다.
한글 24자(72바이트), 25자(75바이트), 일반 영문 비밀번호로 경계를 검증한다.
비밀번호를 조용히 잘라 저장하면 안 된다.

## 검증 기록

Docker에서 임시 PostgreSQL 16·Redis 7을 사용해 다음 범위를 실행했다.

```powershell
.\gradlew.bat -g 'C:/Users/yeka/.gradle' test `
  --tests 'com.yeka.bandapp.user.*' `
  --tests 'com.yeka.bandapp.common.security.*' `
  --tests 'com.yeka.bandapp.band.AuthRateLimitIntegrationTest' --no-daemon
```

초기 점검: **13개 테스트 클래스, 51개 테스트, 실패 0, 오류 0, 건너뜀 0.**
수정 후 같은 명령으로 실행: **13개 테스트 클래스, 59개 테스트, 실패 0, 오류 0, 건너뜀 0.**
통합 테스트의 카카오·메일 등 외부 연동은 테스트 구성에 따른 검증이며 실제 외부 서비스 점검이 아니다.

초기 재현의 임시 파일은 `build/review/`에 있었지만, 수정 전 저장소 API에 의존한다.
수정 후 검증은 위의 정식 테스트와 아래 Flutter 테스트를 사용한다.

```powershell
# client 폴더에서 실행
& 'C:/src/flutter/bin/flutter.bat' test --no-pub test/password_validation_test.dart test/password_reset_flow_test.dart
```

Flutter 테스트 **6개 통과**. 처음부터 있던 `client/pubspec.yaml` 변경과 `.claude/`, `AGENTS.md`는
건드리지 않았다. `docs/TROUBLESHOOTING.md`의 기존 변경을 보존하고 새 해결 기록만 맨 위에 추가했다.

변경한 Flutter 파일 5개 정적 검사: **오류 0·경고 0**, 기존 가입 화면의 쉼표·`const` 관련
정보 수준 안내 9건이 남았다. 저장소 CI 정책처럼 `--no-fatal-infos`로 실행해 통과했다.
`git diff --check`도 통과했다. 전체 프로젝트 테스트나 운영 배포 검증까지 확대한 회차는 아니다.
