## 2. 앱 이름 — 밴듈 (Bandule)

Band + schedule 에서 나온 이름이다. **한국어 표기를 앞세운다.**

영문만 두면 "밴듈/밴둘/반둘레" 중 뭐로 읽을지 정해지지 않는다. 이 앱은 밴드 멤버가 멤버에게
말로 추천해 퍼지는 앱이라, 듣고 검색창에 칠 수 없으면 그 경로가 막힌다.

**다만 워드마크 자리는 영문을 쓴다.** `AppTypography.display` 가 Bebas Neue(라틴 전용)라
한글 글리프가 없어서, 거기에 '밴듈'을 넣으면 폰트가 폴백돼 깨진다. 그래서 `AppConfig` 에
`appName`(밴듈) / `appNameEn`(Bandule) 두 개를 둔다.

| 자리 | 표기 |
|---|---|
| 안드로이드 런처 라벨, 웹 manifest, MaterialApp title | 밴듈 |
| 스플래시·로그인 워드마크(Bebas Neue) | BANDULE |
| 스플래시 워드마크 아래 부제 | 밴듈 |

이름을 바꾸면서 **상수만 갈고 하드코딩된 곳을 놓쳤다** — 로그인 화면의 `'STAGE ON'`,
스플래시의 "앱 이름 미정 · 임시 워크네임". 지적받고 나서야 잡았다. 목업(`example/*.dc.html`)
9곳도 함께 정리해, 이제 저장소에 `STAGE ON` 은 없다.

## 3. 아이콘 — Stick Check

드럼스틱 두 개로 그린 체크 표시. 합주를 확인·기록하는 앱이라는 뜻이고, 주 색 `#FF6A2B` 는
`AppColors.primary` 와 같다.

원본 SVG 는 `client/brand/` 에 있고, 실제 리소스는 `client/tools/render_icons.py` 가 생성한다.
도형이 선 2개 + 원 2개뿐이라 **SVG 파서를 의존성으로 들이지 않고** Pillow 로 같은 도형을
그린다(4배 supersampling). 디자인이 바뀌면 그 스크립트의 `SHAPES` 를 고치고 다시 돌린다.

```bash
cd client && python tools/render_icons.py
```

만든 것: 안드로이드 mipmap 5종(레거시) + 적응형 아이콘(전경 5종 + 그라디언트 배경 벡터,
Android 13+ 테마 아이콘용 monochrome 포함), 웹 favicon·Icon-192/512·마스커블 192/512.
전경은 런처가 원/스퀴클로 잘라내도 안 잘리게 안전 원(66/108dp) 안에 넣었다.

앱 안의 로고도 옛 자리표시(주황 사각형 + 링)였다. `shared/widgets/brand_mark.dart` 의
`BrandMark` 로 교체 — 같은 도형을 `CustomPainter` 로 그려서 에셋 없이 어느 크기로든 쓴다.

## 4. 알림 목록

홈의 종 아이콘이 알림 **설정**으로 가고, 배지는 `final unread = 0;` 로 박혀 있었다.
받은 알림을 볼 곳이 아예 없어 알림 기능이 반쯤 죽어 보였다.

### 백엔드 (V11)

`notification_dispatches` 는 원래 "이미 보냈는가"만 판단하는 **멱등 키**라 문구를 담지 않았다.
문구는 발송 시점에 만들어지고 버려졌다. 그래서 `band_id`·`title`·`body` 세 컬럼을 더하고
발송 시 함께 기록한다.

이력에 문구를 남겨 두면 알림이 가리키던 일정이 나중에 바뀌거나 지워져도 **"그때 받은 그 알림"**
이 온전히 남고, 조회할 때 타입별 조인도 필요 없다. 세 컬럼 모두 NULL 허용이라,
이 변경 이전에 쌓인 알림은 문구가 없어 목록에서 빠진다.

`GET /api/v1/notifications?bandId=&cursor=&size=` — 최신순 커서 페이징.

### 읽음 표시는 서버에 두지 않았다

클라이언트가 **기기에 밴드별 "마지막 확인 시각"** 을 저장하고, 그보다 새 알림을 안 읽은 것으로
센다. 밴드 앱에 서버 읽음 상태까지 둘 이득이 없다고 봤다. 기기를 바꾸면 배지가 초기화되는 것이
단점이다.

화면에는 **열기 직전** 값을 쓴다 — 방금 저장한 값을 쓰면 새 알림 표시가 즉시 사라진다.

## 5. 정산 탭

하단 탭의 "정산"이 누르면 "다음 단계에서 구현" 스낵바만 띄우는 죽은 버튼이었다.

정산 API 는 전부 일정 하나에 매달려 있어(`/reservations/{id}/settlement` 아래 생성·조회·
재계산·납부체크), **밴드 전체를 가로지르는 API 가 없어서** 탭이 갈 곳이 없었다.

멤버가 자기 미납을 확인하려면 캘린더에서 일정을 하나씩 열어봐야 했다. 합주가 주 1~2회면 한 달에
4~8개를 다 뒤져야 한다. 이 앱에서 돈은 가장 예민한 부분이고 미납 독촉 기능도 없으므로,
최소한 본인이 스스로 볼 수 있어야 한다고 판단했다.

`GET /api/v1/bands/{bandId}/settlements` — 최신순 커서 페이징. 각 건에 합주 일시·합주실·총액·
납부인원과 함께 **내 몫·납부 여부**가 담기고, `myOutstandingTotal` 은 그 페이지에서 내가 아직
안 낸 금액의 합이다. 읽기 전용이며 스키마 변경은 없다.

화면은 상단에 "내가 아직 안 낸 돈"을 크게 두고 아래에 목록. 한 건을 누르면 그 일정의 정산
화면으로 간다. 밴드 전체 합계(홈의 '이번 달 정산' 카드)는 여전히 없다 — 홈 카드는 값 대신
이 탭으로 보낸다.

이제 탭 5개가 모두 실제 화면을 가져서, 쓰이지 않게 된 `showSoon` 헬퍼를 지웠다.

## 6. 합주 영상 — 압축 + 스트리밍 + 상한 200MB

합주 영상은 5~6분이 예사인데 상한이 50MB 였다. 실제 크기:

| 화질 | 6분 |
|---|---|
| 폰 기본 촬영 (1080p 17Mbps) | 약 765MB |
| 720p 2Mbps | 약 90MB |
| 480p 1Mbps | 약 45MB ← 옛 상한에 겨우 |

**순서가 중요해서 스트리밍부터 고쳤다.** 그것 없이 상한만 올리면 중저가 기기에서 앱이 죽는다.

1. **스트리밍 업로드** — `Stream.fromIterable([bytes])` 는 한 덩어리 스트림이라 결국 파일
   전체가 메모리에 올라갔다. `uploadMedia` 가 바이트 대신 `Stream` 과 크기를 받고 호출자가
   `file.openRead()` 를 넘긴다. 스트림이라 dio 가 길이를 모르므로 `Content-Length` 를 직접 준다.
2. **상한 200MB** (`MediaPolicy.VIDEO_MAX_BYTES`) — 파일은 presigned URL 로 R2 에 직접 올라가
   백엔드를 거치지 않고, 클라이언트도 이제 스트림이라 양쪽 다 메모리 부담이 없다.
   R2 는 GB당 월 $0.015 에 전송 요금이 없어 비용도 실질적으로 문제되지 않는다.
3. **720p 압축** (`video_compress`) — 6분이 대략 90MB. 합주 영상은 소리가 본체라 720p 면
   충분하다. 30초 넘게 걸릴 수 있어 첨부 칸에 진행률(%)을 보여준다. 실패하면 원본으로 진행하고
   상한 검사에서 걸린다. **크기 검사는 압축 뒤로 옮겼다** — 원본이 상한을 넘어도 압축하면
   들어오기 때문이다. 압축본은 앱 캐시에 쌓이므로 업로드를 마치면 `deleteAllCache` 로 치운다.
   Android/iOS 전용이라 웹은 원본 그대로 간다.

같은 흐름에서 두 가지를 더 고쳤다.

- **글 쓰면서 사진·영상 고르기** — 첨부 영역이 수정 모드에서만 보여서 새 글에는 사진 버튼이
  아예 없었다. 첨부가 글에 매달리는 제약은 그대로 두고 고르는 시점만 앞당겼다: 쓰는 중에
  고르면 "등록 시 업로드"로 대기했다가, 등록 버튼에서 글 생성 → 첨부 업로드를 이어서 한다.
  일부 실패하면 화면을 닫지 않고 실패분만 대기 목록에 남긴다.
- **영상 재생** (`video_player`) — 업로드·삭제·보관기한은 되는데 재생만 없어 "준비 중" 카드가
  떴다. 목록에서는 재생 버튼 카드, 탭하면 전체화면에서 재생(탭 play/pause, 스크러빙 진행바).
  컨트롤 UI 패키지(chewie)는 붙이지 않았다.

## 7. 저장했는데 되돌아가는 버그 — 한 종류였다

참석 여부에서 처음 나왔고, 정산 납부 체크에서 또 나왔다. 같은 원인이라 전수 조사했다.

**원인**: 이 앱의 `FutureProvider` 는 하나도 `autoDispose` 가 아니다 — 캐시가 영구히 남는다.
그래서 저장한 뒤 화면 로컬 상태(`setState`)만 갱신하면, 화면을 벗어나는 순간 로컬 상태가
사라지고 다시 들어올 때 **저장 전 값이 다시 그려진다**. 서버에는 제대로 들어가 있어서
"저장이 안 됐나?" 하고 엉뚱한 곳을 보게 된다.

고친 곳:

| 위치 | 증상 |
|---|---|
| `reservation_detail_screen._respond` | 참석/불참을 바꾸고 나갔다 오면 미정으로 |
| `settlement_screen._togglePaid` | 납부 체크가 다시 들어오면 풀림 |
| `settlement_screen._recalculate` | 재계산 결과가 사라짐 |
| `settlement_screen._create` | 정산 탭의 미납 합계가 안 바뀜 |
| `recurring_form_screen._submit` | 정기 일정 등록 후 목록·캘린더·홈이 그대로 |

정산 쪽은 상세 화면과 **정산 탭** 두 캐시를 함께 비워야 한다(`_refreshCaches`).
정기 일정은 규칙만이 아니라 회차(일정)까지 만들어지므로 캘린더·홈도 비운다.

**다시 안 나게**: `client/tools/check_cache_invalidation.py` 를 뒀다. 쓰기 메서드를 찾아
그 안에서(또는 그 메서드를 부르는 쪽에서) 캐시를 비우는지 본다. 헬퍼로 쪼갠 경우도 따라간다.

```bash
cd client && python tools/check_cache_invalidation.py
```

현재 33개 화면 파일 통과. 무효화를 일부러 지우면 그 메서드를 집어내는 것까지 확인했다.

## 9. 알려진 이슈 / 다음에 할 것

### 9-A. 신고 레이트리밋 테스트가 간헐적으로 실패한다

`ReportIntegrationTest.reports_are_rate_limited_per_user()` 가 **전체 실행에서 한 번 실패**했다.
단독 실행과 전체 재실행에서는 통과했다.

```
Expecting actual: 0 to be greater than: 0     (limitHits == 0)
```

12번의 신고 요청 중 429가 한 번도 안 나왔다는 뜻이다. 이 테스트는 루프 안에서 `signup()` 을
12번 호출하는데, `AuthRateLimitInterceptor` 의 가입 레이트리밋이 IP 단위라 전체 실행 시 다른
테스트들이 먼저 소진해 버리면 이 루프의 signup 이 429로 떨어지고, 그 뒤 신고 요청이 429가 아닌
다른 코드가 되는 것으로 **추정**된다(확인 안 했다).

고치는 방향: 루프 안 signup 의 응답 코드를 찍어 원인을 확정한 뒤, 레이트리밋 상태를 테스트
시작 시 비우거나 대상 사용자를 미리 만들어 두고 신고만 반복하도록 바꾼다. 테스트가 검증하려는
것("계정당 신고 상한이 동작한다")은 유지해야 한다.

### 9-B. 그대로 남은 것

[client-SCREENS.md](client-SCREENS.md) §4 "알려진 제약" 표가 최신이다. 큰 것만 옮기면:

- **출시 전 필수** — 패키지명이 `com.example.bandapp_client` 다(구글 플레이가 거부한다).
  바꾸면 카카오 콘솔 플랫폼 등록도 다시 해야 한다. 릴리스 서명 설정·ProGuard 활성화도 아직.
- **PREMIUM 만료 자동 강등 배치가 없다**(`PlanService` TODO) — 기한이 지나도 계속 PREMIUM.
  돈이 걸린 문제라 우선순위가 높다.
- 미납 독촉(백엔드 API 없음), 홈 '이번 달 정산' 집계, 알림 딥링크, 정기 규칙 상세/수정,
  캘린더 주간 뷰, 셋리스트 완료 체크, 네이버 로그인, 밴드 장르·파트, 약관 동의 기록.
