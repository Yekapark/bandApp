## 1. [P2] 마지막 반복 회차를 앞당기면 원래 날짜에 회차가 다시 생긴다

**영향** — 사용자는 한 번의 합주 날짜를 옮겼는데, 회차 연장 작업이 원래 날짜의 합주를
추가로 만들어 두 일정이 남는다. 잘못 추가된 회차에는 참석 행과 합주실 사용 횟수도 붙는다.

**위치**

- `src/main/java/com/yeka/bandapp/recurring/service/RecurringRuleService.java:190`
- `src/main/java/com/yeka/bandapp/reservation/service/ReservationDirectoryService.java:108`
- `src/main/java/com/yeka/bandapp/reservation/repository/ReservationRepository.java:98`

**재현** — 주간 규칙을 등록해 8주 범위 회차를 만든다. 가장 늦은 회차를 API로 하루 앞당긴다
(HTTP 200). 같은 규칙의 `extendRule`을 실행하면 1건을 새로 만들고, 원래 날짜의 회차가 돌아온다.
옮긴 회차도 그대로 있어 전체 회차 수가 하나 증가한다. 테스트는 날짜나 DB 행을 직접 조작하지 않았다.

```text
update=200, extension added=1, original slot regenerated
```

**원인** — 연장 기준인 “이미 생성한 마지막 회차”와 중복 확인에 사용자가 바꿀 수 있는
`startAt`을 사용한다. 원래 어느 회차를 옮겼는지 저장하지 않아, 시작 시각을 앞당기면 원래
회차를 아직 만들지 않은 것으로 판단한다. `BUILD_PLAN.md`의 “개별 회차 수정은 해당 일정만
변경하고 규칙은 유지”와 맞지 않는다.

**수정 제안** — 원래 생성 슬롯을 변경되지 않는 값으로 보존하고, 연장 위치와 재생성 방지를
그 값으로 판단한다. 화면의 실제 합주 시각은 자유롭게 변경할 수 있어야 한다.

## 2. [P2] 반복 회차를 다른 회차와 같은 시작 시각으로 옮기면 서버 오류가 난다

**영향** — 겹치는 일정도 저장해야 하는 앱인데, 같은 반복 규칙에 속한 회차끼리는 시작
시각이 같아지면 수정이 실패한다. 다른 합주실로 옮겨도 같은 시작 시각이면 제약에 걸린다.

**위치**

- `src/main/resources/db/migration/V5__recurring.sql:58`
- `src/main/java/com/yeka/bandapp/reservation/service/ReservationService.java:175`

**재현** — 같은 주간 규칙의 첫째 회차를 둘째 회차의 시간으로 수정한다.
응답은 HTTP 500이고, 첫째 회차의 변경은 롤백된다. DB 오류는 `ux_reservations_rule_slot`
유니크 제약 충돌이다. 단발 일정끼리의 겹침 저장은 기존 테스트에서 정상이다.

```text
update=500, moved occurrence rolled back
```

**원인** — 배치 중복 생성을 막으려고 만든 `(recurring_rule_id, start_at)` 유니크 인덱스가
일반 일정 수정에도 적용된다. “원래 같은 회차인가”와 “현재 같은 시각에 진행하는가”를 같은
값으로 판정한다. 스키마 주석은 겹침 차단이 아니라고 설명하지만, 이 수정 경로에서는 실제로
저장을 막으므로 `BUILD_PLAN.md` 2장 2번과 불일치한다.

**수정 제안** — 1번과 함께 원래 생성 슬롯 기준으로 유니크 제약을 옮긴다. 현재 `startAt`의
겹침은 저장을 허용하고 경고로만 반환한다. 오류를 409로 바꾸거나 인덱스만 지우는 것으로는
겹침 허용과 배치 중복 방지를 동시에 해결할 수 없다.

## 3. [P2] 전체 규칙 삭제와 개별 회차 취소가 겹치면 사용 횟수를 두 번 뺀다

**영향** — 합주실의 이용 횟수와 정렬 순서가 실제 기록과 달라진다.
활성 일정이 한 건 남아 있는데도 이용 횟수가 0이 되는 상태를 확인했다.

**위치**

- `src/main/java/com/yeka/bandapp/reservation/service/ReservationDirectoryService.java:138`
- `src/main/java/com/yeka/bandapp/reservation/repository/ReservationRepository.java:107`

**재현**

1. 같은 합주실에 미래 반복 회차 1건과 별도 단발 일정 1건을 만든다. 사용 횟수는 2다.
2. 개별 회차 취소가 사용 횟수를 줄인 뒤 커밋 직전에 기다린다.
3. 다른 트랜잭션에서 규칙 삭제를 시작한다. 아직 커밋되지 않은 취소를 보지 못해 같은 회차를
   취소 대상으로 읽는다. 실제 DB 잠금 대기를 확인한 뒤 첫 요청을 커밋한다.
4. 규칙 삭제도 끝나면 단발 일정은 `CONFIRMED`로 남지만 사용 횟수는 0이다.

```text
live reservations=1, room usage=0
```

**원인** — 개별 취소는 일정 행을 잠그지만, 전체 규칙 삭제는 규칙 행만 잠그고 회차는 일반
조회로 읽는다. 방의 횟수 갱신이 원자적이어도 같은 회차를 두 번 취소 처리하는 판단은 막지
못한다. 0 이하로 내려가지 않게 하는 보정은 오집계를 숨길 뿐이다.

**수정 제안** — 규칙 삭제도 대상 일정 행의 상태를 잠금 아래 확인하고, 실제로 취소된
회차만 집계한다. 개별 일정 변경과 함께 사용할 규칙·일정·합주실 잠금 순서를 정해야 한다.
관련 일정 수정이 기존 규칙 잠금과 충돌하는 경우도 함께 검증한다.

## 4. [P2] 셋리스트 곡 편집이 동시 순서 변경을 덮어쓴다

**영향** — 다른 멤버가 바꾼 연주 순서가 곡 제목을 저장하는 순간 원래대로 돌아간다.
두 곡의 순서 번호가 모두 1인 상태도 생긴다. 순서 변경 요청 자체는 HTTP 200으로 성공한다.

**위치**

- `src/main/java/com/yeka/bandapp/reservation/service/SetlistService.java:82`
- 같은 파일 `103` — 재정렬 시 조회·갱신.

**재현** — A(1번), B(2번)가 있는 셋리스트에서 A 제목 편집을 커밋 직전에 대기시킨다.
다른 요청으로 B→A 순서를 저장한다(200, A는 2번). 제목 편집을 커밋하면 A가 다시 1번이
되어 A와 B 모두 1번으로 남는다.

```text
reorder=200, orderNo changed back to 1, duplicate order=1
```

**원인** — 제목 편집이 엔티티 전체 갱신으로 저장되어, 편집 시작 때 읽은 `orderNo`도 함께
덮어쓴다. 같은 일정의 곡 추가·편집·삭제·재정렬 사이에 공통 잠금이나 충돌 검사가 없다.

**수정 제안** — 같은 일정의 셋리스트 변경을 직렬화하고 잠금 뒤 현재 곡 상태를 읽는다.
곡 편집과 재정렬뿐 아니라 추가·삭제도 같은 순서를 사용하도록 검증한다.

## 다음 수정 범위

1·2번을 함께 해결하는 구체적 제안은 반복 회차의 `originalStartAt`(원래 슬롯)을 별도 보존하는
것이다. 생성 때만 지정하고, 연장 기준·중복 제약은 이 값에 걸며 실제 일정의 `startAt`은
자유롭게 수정한다. 새 필드와 유니크 제약 교체에는 Flyway 마이그레이션이 필요하다.
기존에 이미 옮긴 회차는 현재 시각만으로 원래 슬롯을 정확히 복원할 수 없으므로 이력의 처리
방침도 정해야 한다. 아직 이 구조 변경이나 운영 데이터 수정은 수행하지 않았다.

3·4번은 현재 도메인 구조에서 변경 작업의 잠금과 조회 순서를 정리하는 수정이다.
과거 정산 보존·겹침 허용·권한 검사를 그대로 유지하면서 위 재현들을 회귀 테스트로 바꾼다.

운영 서버·실제 사용자 데이터는 조회하지 않았으며 커밋·배포도 수행하지 않았다.
앞 회차의 인증·밴드 수정 및 사용자의 기존 변경은 보존했다.
