# 2차 점검 — 밴드·초대·권한

- 날짜: 2026-09-13
- 기준: `5a84f31` 및 현재 작업 폴더(1차 인증 수정 포함)
- 범위: 밴드 생성·조회·설정·삭제 권한, 멤버 탈퇴·추방·위임, 초대 발급·참여, 계정 탈퇴 후 밴드 정리.
- 초기 점검: 기존 테스트 47개 통과. 별도 실제 DB 재현에서 문제 3개 확인.
- 상태: **세 문제 수정·검증 완료.** 밴드·계정·인증 **21개 클래스, 123개 테스트 통과**.
  실패·오류·건너뜀 0. 이 중 밴드 범위는 9개 클래스·66개 테스트이며 동시 요청 검증 16개를 포함한다.

## 반영한 변경

- 위임·탈퇴·추방·계정 정리·초대 변경·설정 변경은 밴드 행을 먼저 잠근 뒤 현재 상태를 읽는다.
  밴드 DB 삭제도 같은 순서로 잠근다. 계정 삭제의 여러 밴드는 ID 오름차순으로 처리한다.
- 마지막 밴드장이 계정을 삭제하면 초대를 무효화한다. 참여도 활성 밴드장이 없으면
  `410 INVITE_REVOKED`로 거절하므로 수정 전에 남은 유효 코드도 빈 밴드를 다시 열 수 없다.
- 계정 삭제와 밴드 생성·가입은 사용자 행을 먼저 잠근다. 삭제된 사용자에게 새 멤버십이
  남지 않도록 하며, 외래키 검증과 충돌하지 않는 PostgreSQL `FOR NO KEY UPDATE`를 쓴다.
- 새로운 라이브러리·엔티티 필드·마이그레이션은 없다. 커밋·운영 배포는 수행하지 않았다.

아래 재현과 원인은 **수정 전 상태**의 기록이다. 위치는 메서드 기준으로 찾아야 하며
표시된 줄 번호는 수정 전 기준이다.

## 1. [P2] 위임과 멤버 탈퇴가 겹치면 밴드장이 사라진다

**영향** — 멤버가 남아 있는데도 밴드장 전용 기능을 사용할 사람이 없어진다.
설정 변경·초대 발급·재위임을 정상 API로 복구할 수 없다.

**위치**

- `src/main/java/com/yeka/bandapp/band/service/BandMemberService.java:57` — 탈퇴 시 역할 확인과 변경.
- 같은 파일 `84` — 위임 시 두 멤버의 역할 변경.
- `src/main/resources/db/migration/V2__band.sql:41` — 밴드장 부분 유니크 인덱스.

**재현**

1. A가 밴드장이고 B가 일반 멤버인 밴드를 만든다.
2. B의 탈퇴 처리가 B를 일반 멤버로 읽고 `leftAt`을 변경한 뒤, 커밋 직전에 대기한다.
3. A가 B에게 밴드장을 위임한다. HTTP 200, 위임 트랜잭션 커밋.
4. B의 탈퇴 트랜잭션도 커밋한다.
5. 활성 멤버는 A 한 명이지만 활성 밴드장은 0명이다. A의 설정 변경은 403이다.

```text
delegation=200, leave committed, activeMembers=1, activeLeaders=0
```

**원인** — 위임·탈퇴가 같은 밴드의 변경을 직렬화하지 않고, 조회한 역할도 변경 직전에 다시
확인하지 않는다. 멤버 엔티티에 버전 충돌 검사가 없어 오래된 상태로 저장할 수 있다.
유니크 인덱스는 밴드장이 **최대 한 명**인 것만 보장한다. 주석의 “정확히 한 명” 설명과 달리
0명이 되는 상황은 막지 못한다.

**수정 방향** — 밴드 단위의 공통 DB 잠금을 잡은 뒤 멤버십·역할을 조회하고 변경한다.
위임뿐 아니라 자발적 탈퇴·추방·계정 탈퇴도 같은 순서를 따라야 한다.
계정 탈퇴처럼 여러 밴드를 처리할 때는 잠금 순서도 일정하게 정한다.

## 2. [P2] 동시에 초대를 발급하면 유효한 코드 두 개가 남는다

**영향** — 새 초대를 발급하면 기존 코드가 무효화된다는 약속이 깨진다.
화면의 “현재 코드”에는 하나만 보이지만 다른 코드로도 참여할 수 있다.

**위치** — `src/main/java/com/yeka/bandapp/band/service/BandInviteService.java:61`.

**재현**

1. 아직 초대가 없는 같은 밴드에 발급 요청 A를 시작한다.
2. A가 기존 초대를 무효화하고 새 코드를 저장한 뒤, 커밋 전에 대기한다.
3. 요청 B도 같은 밴드에 새 코드를 발급하고 커밋한다.
4. A도 커밋한다.
5. 무효화되지 않은 코드가 두 개이며, 서로 다른 사용자가 각각의 코드로 참여하면 둘 다 HTTP 200이다.

```text
activeCodes=2, firstCodeJoin=200, secondCodeJoin=200
```

**원인** — “기존 초대 무효화 → 새 초대 삽입”이 한 트랜잭션이어도 다른 발급 요청이 끼어들 수 있다.
서로 아직 커밋되지 않은 초대를 보지 못하고 각각 삽입한다. 코드 문자열의 전역 유니크 제약은
서로 다른 두 코드가 같은 밴드에서 동시에 유효한 것을 막지 않는다.

**수정 방향** — 초대 발급·무효화도 밴드 단위 잠금 아래 순서대로 처리한다.
동시 발급 후 유효 코드가 하나이고 이전 코드로 참여할 수 없는지 검증한다.

## 3. [P2] 마지막 밴드장 계정 삭제 후에도 옛 초대로 관리자 없는 밴드에 들어간다

**영향** — 접근 불가능한 상태로 남겨야 하는 빈 밴드에 다시 참여할 수 있다.
새 참여자는 일반 멤버여서 밴드 정보를 읽을 수 있지만 초대 발급 같은 관리 기능은 사용할 수 없다.

**위치**

- `src/main/java/com/yeka/bandapp/band/service/BandMemberService.java:117` — 계정 탈퇴 정리.
- `src/main/java/com/yeka/bandapp/band/service/BandInviteService.java:95` — 초대 참여.

**재현** — 혼자 있는 밴드장이 초대를 발급하고 계정을 삭제한다. 활성 멤버 0명을 확인한 뒤,
다른 계정이 기존 코드로 참여한다. 참여·밴드 조회는 200, 활성 밴드장 수는 0, 초대 발급은 403이다.
이 문제는 동시 요청 없이 순서대로 실행해도 발생한다.

```text
join=200, read=200, activeLeaders=0, issueInvite=403
```

**원인** — 마지막 멤버의 계정 탈퇴 시 초대코드를 무효화하지 않는다. 참여 경로도 밴드에
활성 밴드장이 남아 있는지 확인하지 않고 일반 멤버를 추가한다.
`docs/BACKLOG.md` §1.9의 “빈 밴드는 접근 불가라 사실상 소멸”이라는 선택과 실제 동작이 다르다.

**수정 방향** — 마지막 멤버가 빠질 때 초대를 무효화하고, 참여 시에도 활성 밴드장이 없는
밴드는 거부한다. 탈퇴와 참여가 겹쳐도 같은 결과가 나도록 앞의 밴드 잠금과 함께 처리한다.
데이터 영구 삭제나 새 멤버의 자동 밴드장 승격은 이번에 권장한 수정 범위가 아니다.

- 정식 권한 검사로 편입: **다른 밴드의 밴드장**으로 다음 10개 경로에 접근하면 모두 HTTP 403.
  밴드 조회, 멤버 목록, 현재 초대 조회, 초대 발급, 초대 무효화, 설정 변경, 위임,
  자발적 탈퇴, 멤버 추방, 밴드 삭제. 존재하지 않는 밴드의 초대 발급도 기존처럼 403이다.
- `git diff --check` 통과. 이번 회차는 Flutter 코드를 변경하지 않았다.

동시 요청 검증은 시간만 기다리는 방식이 아니라 두 번째 트랜잭션이 실제 DB 잠금에 막힌
상태임을 확인한 다음 첫 요청을 커밋한다. 이후 멤버 수·밴드장 역할·밴드의 밴드장 ID와
도메인 오류를 검사한다. 두 계정 동시 탈퇴는 두 사용자 행을 먼저 잠근 뒤 함께 시작한다.

## 수정 전 별도 재현의 방식과 한계

임시 파일 `build/review-bands/BandReviewProbeTest.java`와 `review.init.gradle`을 사용했다.
실제 애플리케이션 서비스·PostgreSQL 16·Redis 7을 실행했다. 계정 삭제 후 초대 참여와
타 밴드 권한 확인은 HTTP로, 두 경합은 한 서비스 트랜잭션을 커밋 직전에 대기시키고
다른 HTTP 요청을 완료하는 방식으로 재현했다. DB 상태를 직접 조작해 결과를 만든 것은 아니다.

임시 검사 4개는 **잘못된 상태가 실제로 생겼음을 확인하는 재현 3개와 정상 권한 검사 1개**다.
4개 통과를 기능이 올바르다는 뜻으로 해석하면 안 된다. **수정 후에는 위의 정식 테스트만
실행한다.** 임시 재현은 잘못된 상태와 수정 전 요청 순서를 기대하므로 현 코드의 검증용이
아니다. 임시 파일은 `clean` 시 삭제될 수 있다.

운영 서버·실제 R2 객체는 점검하지 않았다. 외부 서비스 상태나 모든 동시 실행 조합이
정상이라고 판단한 결과는 아니다. 앞 회차의 인증 수정과 기존 사용자 변경은 그대로 보존했다.
이미 밴드장이 없어진 운영 데이터의 조사·복구는 수행하지 않았다. 이번 변경은 재발 방지와
빈 밴드 초대 참여 차단이며, 잘못된 멤버 역할을 자동으로 정하는 복구 절차를 포함하지 않는다.
